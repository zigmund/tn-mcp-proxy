# tn-mcp-proxy: security audit (second round)

Line numbers in the `file:line` evidence below refer to the baseline commit `7ac37ab`, not to the current code. The addendum cites `1255d35` where it says so.

- **Scope:** `internal/{oauth,seal,tokens,proxy,server,httplog,ratelimit,config,certreload,credcheck,logging}`, `cmd/`, `deploy/`, README.md, docs/*.md. Special attention went to the code added since the first audit (`git diff 3eeecc2..7ac37ab`: credential validation, `internal/credcheck`, proxy limits and the re-check on tool errors, IPv6 tiers and the global authorize ceiling, the revocation set, `allowed_values`, read deadline, HSTS, transport and TTL validation).
- **Baseline:** main at `7ac37ab`. The previous audit was at `3eeecc2` ([first report](audit-2026-10-3eeecc2.md), findings F-01..F-07 and I-01..I-07).
- **Method:** I first did an independent white-box review of the full flow (DCR -> authorize GET/POST with credential check and allow-list -> token (code, refresh) -> proxied call with limits, tool-error inspection and re-check). Only then did I re-read the old findings and verify each one. `go vet ./...` is clean, `go build ./cmd/tn-mcp-proxy` succeeds and `go test ./...` passes. PoC tests ran against a copy of the repository at `7ac37ab`. The live upstream was not contacted.
- **PoCs:** the PoC tests (14 at `7ac37ab`: new findings, regressions of the previous findings, and one ruled-out hypothesis) were run privately and are not published. Equivalent regression tests for the fixes live in the repository; the report names them where relevant ("repo tests").
- **Re-run at `1255d35`:** the PoCs were adapted to the fixed code and re-run. See the [Addendum](#addendum-status-at-1255d35).

## 1. Summary

The fixes for the first round hold up.
- Every previous finding is fixed, or accepted and documented. The regression PoCs (run privately) no longer reproduce F-01, F-02, F-03, F-05, F-06 or F-07.
- The new code is careful:
  - The credential check fails closed, never follows redirects and bounds bodies.
  - The tool-error inspection is bounded in size and decompression, and never reads the error text.
  - The revocation set is immune to LRU pressure.
  - The proxy uses header and method allow-lists.
  - The limits refund correctly.
- I found no Critical, High or Medium issue that is exploitable in the recommended configuration (`allowed_values` **and** `validate`).

The weaknesses are again at the edges, and mostly at the seams between features:

- **The allow-list can be configured without the credential check (N-01).** `allowed_values` is meant to go on the *non-secret* half of a key pair. Without `validate`, nothing ties the token to the secret, so the allow-list only proves knowledge of the API key. The proxy relays request bodies verbatim. The Tradernet MCP server documents that credentials may also be passed as tool parameters. The allow-list therefore does not reliably close the open relay the README warns about. Startup does not warn about this combination.
- **The global authorize ceiling is spent by requests that can never yield a code (N-03).** This lets anyone delay the owner's (re)connection in a single-user deployment.
- Some smaller seams (N-04..N-06) and doc claims are out of step with the code.

| Severity | Count |

If that precedence holds, N-01 is Medium: it re-opens F-01 for a deployment whose operator believes it is restricted.

### N-01: `allowed_values` without `validate` restricts only knowledge of the API key (Low; Medium if precedence confirmed)

**Evidence**
- `internal/config/config.go:754-758`: `validate` is optional for every upstream, including ones with `allowed_values`. `validateAllowed` (`config.go:764-790`) requires the list to be on a `secret: false` credential, by design the identifying half of a key pair.
- `cmd/tn-mcp-proxy/allowlist.go:11-19`: startup warns only when an upstream has **no** allow-list. Nothing warns about an allow-list without `validate`.
- `internal/oauth/authorize.go:272-284`: with an allow-list and no `validate`, `POST /oauth/authorize` issues a code for the allow-listed key paired with **any** secret.
- `internal/proxy/proxy.go:334-374`: the request body and (when the upstream URL has no query) the client query string are forwarded unchanged. Only headers are filtered.
- Upstream fact: the Tradernet MCP server's own published instructions say credentials can be passed "via MCP transport headers (X-TN-API-Key / X-TN-API-Secret / X-TN-SID) or as explicit tool parameters". Its tool schemas describe `api_key`/`api_secret` arguments as a "stdio fallback" and say the header is preferred. Tool-argument credentials are therefore a documented upstream feature. **Whether they take precedence over the injected headers is untested.**
- Docs: the README CAUTION box and `docs/configuration.md` "Restricting access" present `allowed_values` as *the* restriction and show it without `validate`. The README "Configure" example and `deploy/config.example.yaml` do include `validate`.

**Impact**
- In this configuration the allow-list does not bind the token to the owner's account. It binds it to knowledge of the owner's API key. The README treats that key as non-secret, and `/etc/tn-mcp-proxy/config.yaml` is installed world-readable (`0644`), so local users of the host can read it.
- The resulting token carries a wrong secret. The proxy then relays the token holder's request bodies from the operator's IP.
- If the upstream lets argument credentials win over the injected headers, the deployment is the open relay the README warns about (attribution of trading activity to the operator's IP), while the operator believes it is restricted.
- If the headers win, the impact reduces to tokens that fail upstream, plus the cost of their re-checks.

**Recommended fix**
1. Make `allowed_values` without `validate` a config error, or at minimum a loud startup warning. Say in "Restricting access" that the allow-list is effective only together with `validate`.
2. Document that the allow-list gates **token issuance**, not request content: a token holder can put any arguments into a request body.
3. Optional defence in depth: an upstream setting such as `forbidden_arguments: [api_key, api_secret]` that rejects `tools/call` requests whose `params.arguments` contain those names. This needs bounded JSON inspection of POST bodies, similar to the response inspection that already exists.
4. Optional: verify with Tradernet (or a test account) which source wins when both a header and an argument are present, and record the answer in the docs.

**Reproduction (private PoC)**
- An allow-list on the API key with no `validate`: the owner's API key plus an arbitrary secret yields a token.
- A `tools/call` of a read-only tool with credential-named arguments reaches the (fake) upstream byte for byte.
- Control: with `validate` configured, the same submission gets 400 and no code.

### N-03: The global authorize ceiling is spent by submissions that can never yield a code (Low)

**Evidence**
- `internal/oauth/oauth.go:88` and `internal/oauth/ratelimit.go:139-153`: the per-IP tiers and the unkeyed global bucket are charged in the middleware, before `authorizeSubmit` runs.
- `internal/oauth/authorize.go:272-276`: foreign keys are refused by the allow-list (no upstream call, no code) only after that charge. The same applies to submissions with a bad sealed request, invalid input and upstream-rejected credentials.

**Impact.** In a single-user deployment with `allowed_values`, the ceiling exists only to bound live codes, but requests that cannot produce a code use it up. A flood from enough sources keeps the global bucket empty: about 83 IPv4 addresses, or 5 to 6 IPv6 /48s at the defaults (docs/architecture.md, "Cache filling"). While it lasts, the owner's own submission gets 429 and the owner cannot (re)connect the connector. The docs acknowledge "delays new logins", but not that in an allow-listed deployment every one of those requests is useless to the attacker as well as harmful to the owner.

**Recommended fix.** Charge the global bucket at the point where a code is about to be sealed, after the allow-list and the credential check. Refund nothing earlier. Keep the per-IP tiers in the middleware. The cache bound is unchanged, because only code-issuing requests can occupy code slots. The upstream credential check remains bounded by the per-IP tiers and the 16-slot checker semaphore. If an unkeyed bound on upstream checks is still wanted, add a separate bucket for "submissions that reach the upstream".

**Reproduction (private PoC, ceiling shrunk to 5/min):** five foreign-key submissions from five addresses each get 400, and the upstream is never contacted. The owner's correct submission from a sixth address then gets 429.

### N-04: The per-grant key includes the unvalidated optional SID (Info)

**Evidence**
- `internal/proxy/limits.go:213-234` (`grantKey`) hashes all injected credential headers, including optional ones.
- `docs/configuration.md:197-201`: `get_auth_info` does not check `X-TN-SID`, so any SID string passes `validate`.

**Impact.** One valid key pair combined with N different SID strings gets N independent per-grant budgets (`limits.token`, `limits.max_concurrent_per_token`). This weakens the claim (`docs/configuration.md:443-447`) that one set of credentials is one budget. In an open deployment one user can use it to hold many more in-flight slots than intended (SSE streams, slow bodies). Only `limits.ip` and the global `max_in_flight` still bound them. With an allow-list, only the owner is affected.

**Recommended fix.** Compute the grant key from the non-optional credentials only (or from the credentials that `validate` actually verifies), and document that.

**Reproduction (private PoC, `max_concurrent_per_token: 1`):** a second stream with the same SID gets 429; with a different SID it gets 200.

### N-05: Allow-list timing reveals the list (Info)

**Evidence**
- `internal/oauth/authorize.go:272-276`: an allow-list mismatch returns immediately.
- `authorize.go:278`: an allow-listed key with a wrong secret goes through the upstream round trip (about 0.4 to 1 s with Tradernet, per the docs).
- `docs/architecture.md:72` and `docs/configuration.md:121` claim the response "does not reveal that a list exists". Status code and message are identical, but timing is not.

**Impact.** Small. The comparison itself is constant-time (`internal/config/config.go:277-294`), so no value leaks byte by byte. An observer can tell that a list exists, and whether a candidate API key is the listed one. The latter is useful only with a candidate list of real keys, and the secret is still required.

**Recommended fix.** Correct the doc claim. Optionally delay allow-list rejections to a typical check latency.

**Reproduction (private PoC, fake upstream with a 300 ms delay):** both submissions get 400; the foreign key takes about 0.1 ms and the allow-listed key with a wrong secret about 300 ms.

### N-06: Refresh keeps working after the re-check confirms rejected credentials (Info)

**Evidence**
- `internal/proxy/toolerror.go:120-138`: a confirmed rejection turns the response into `401 invalid_token`.
- `internal/oauth/token.go:248-341`: the refresh grant does not consult the re-check verdict, so it issues a new pair with the same credentials (`token.go:340`).
- README:207 and `docs/architecture.md:495` state that the client "re-runs the flow".

**Impact.** Availability and usability only. An MCP client that answers a 401 by refreshing first gets fresh tokens, hits the cached "rejected" verdict again and loops until the refresh chain ends, instead of showing the user the credentials form. I did not verify how claude.ai and ChatGPT behave.

**Recommended fix.** In the refresh grant, look up the re-check verdict cache for the token's upstream and credentials. On a live "rejected" verdict, answer `invalid_grant` so the client must run the full authorization. Alternatively, document the limitation.

**Reproduction (private PoC):** the tool call gets 401, the refresh gets 200, and the call with the new token gets 401 again.

### N-07: Hardening notes (Info)

- **Proxy environment variables.** Both upstream transports are clones of `http.DefaultTransport` and keep `Proxy: ProxyFromEnvironment` (`internal/proxy/proxy.go:163-171`, `internal/credcheck/credcheck.go:75-87`).
  - With an `https` upstream, an environment proxy only sees CONNECT.
  - With `allow_insecure_http` and an `http` upstream, it would see the plaintext credential headers.
  - Consider setting `Proxy: nil` explicitly, or documenting it.
- **Re-check cost during an upstream outage.** "No verdict" is cached for 5 s (`internal/proxy/recheck.go:29`), so a token whose calls keep failing costs up to about 12 sessions a minute during an outage, not one. Saturation (8 concurrent checks) is not cached at all. The docs' "at most one session per minute" holds only while the upstream answers.
- **Shareable authorize URLs.** An authorize URL (client id, attacker-chosen PKCE challenge and state) has no expiry and is not bound to a browser. It can be handed to a victim, who sees a genuine page naming claude.ai or chatgpt.com. Whether the victim's credentials end up in the attacker's connector depends on whether the client binds `state` to the browser session that started the flow; that is outside the proxy. The page hint ("Only continue if you started this connection yourself") is the right mitigation. A short note in "Security notes" would complete it.
- **Upstream response headers** are passed through except `Set-Cookie` (and `Strict-Transport-Security` with built-in TLS). No impact found, because the MCP path requires a bearer header and answers browser preflights with 405.

## Positive observations

- The credential check is a careful, minimal MCP client. It never follows redirects (credentials cannot leave for another host), parses SSE per WHATWG, bounds every body, separates "rejected" from "unavailable" so it fails closed, strips `url.Error` before logging, and releases its slot before the best-effort DELETE.
- The tool-error inspection never changes bytes it does not replace. It replays a too-large body from the buffered prefix, caps the decoded gzip size, and leaves SSE and GET untouched.
- The revocation set is the right shape: keyed per process, never evicted for room, and failing closed only for unknown families.
- The limits refund precisely (IP tokens, per-grant tokens, slots) and are keyed without retaining tokens or credential values.
- Allow-list values are kept out of error messages, compared in constant time, and re-checked at refresh and on every proxied request, so removing a value cuts existing tokens off after a restart.
- The `X-NtApi-*` pre-signed headers that the upstream would honour are dropped by the header allow-list, so a token holder cannot override the injected credentials through headers.
- Config validation is thorough: https enforcement, TTL caps, weak-key rejection, forbidden credential headers, path overlap checks, and errors that never echo values.

---

## Recommendations summary (priority order)

1. **N-01:** reject (or loudly warn about) `allowed_values` without `validate`. Document that the allow-list gates token issuance, not request content. Consider a `forbidden_arguments` filter for credential-named tool arguments. Find out the upstream's header-versus-argument precedence.
2. **N-03:** charge the global authorize ceiling only for submissions that are about to issue a code.
3. **N-04:** leave optional, unvalidated credentials out of the grant key.
4. **N-06:** make the refresh grant honour a live "rejected" re-check verdict.
5. **N-05, N-07, section 5:** align the docs (timing claim, re-check cost during outages, shareable authorize URLs, allow-list + validate pairing); set `Proxy: nil` on the upstream transports, or document it.

### New items found in the re-check

**N-09: one doc sentence still says bodies are streamed (Info, documentation). Fixed in PR #38: the "Body cap" bullet now says that bodies are streamed, except on an upstream with `forbidden_arguments`, where each POST body is read whole into memory.** With `forbidden_arguments` set, every POST body is read whole into memory while the request holds its slots (`internal/proxy/toolargs.go:42,64-66`). This is documented in the `limits.max_request_body` row (`docs/configuration.md:518`: worst case about 3 to 4 times `max_in_flight` x `max_request_body`), in "Forbidden tool arguments" and in `docs/architecture.md:473`. At `1255d35` the "Body cap" bullet of "Proxy limits" (`docs/configuration.md:565`) still said "Bodies are streamed, not buffered".
- The example config enables `forbidden_arguments`, so with the defaults the theoretical worst case is in the tens of GiB.
- Only token holders can drive it, which with an allow-list means only the owner (or someone who stole the owner's token).
- Suggested fix: correct the sentence. Optionally give inspection its own lower cap or a global byte budget, so upload-sized bodies do not set the memory ceiling for every request.
- Reproduction (private PoC): a chunked 2 MiB body reaches the upstream with an exact `Content-Length`.

**N-10: structural keys are matched case-sensitively (Info, documented assumption). Fixed in PR #38: a key in any message, or in a `tools/call`'s `params`, that equals `method`, `params` or `arguments` only under case folding is now refused with `-32600`, so the inspection fails closed.** `method`, `params` and `arguments` were recognised only with exact spelling (`internal/proxy/toolargs.go:171-182,202-206`). At `1255d35` a message that spelled them `METHOD`/`PARAMS`/`ARGUMENTS` (and had no exact-case key) was forwarded uninspected.
- That was correct for upstreams with exact-key JSON-RPC parsing. That is the norm, and the Tradernet tool schemas look like a Python/pydantic implementation. The docs state the assumption (`docs/configuration.md:168-170`).
- It would have been a gap only behind an upstream that matches these keys case-insensitively, for example Go `encoding/json` struct decoding.
- Suggested fix, optional and cheap, to make the inspection fail closed here too: refuse a message containing a key that equals `method`, `params` or `arguments` case-insensitively but not exactly.
- Reproduction (private PoC): at `1255d35` a message with case-variant structural keys was forwarded uninspected.

**Independent look at the `forbidden_arguments` inspection.**
- The parser checks are sound: strict validation (`utf8.Valid` + `json.Valid`, only JSON whitespace trimmed), a token-level walk that sees duplicate keys, refusal of duplicate structural keys, and every batch element required to be an object.
- Key comparison runs on decoded keys (`\u` escapes cannot hide a name), and argument names match case-insensitively.
- Bodies go through the request cap, compressed bodies are refused, the forwarded body is the identical bytes, and logs never contain values.
- Residual limits, all documented or minor:
  - Only top-level `arguments` and only `tools/call` are checked. That is sufficient for upstreams whose credential parameters are top-level tool arguments, as Tradernet's are.
  - Positional (array) `params` are passed through. MCP requires an object, so they are not a `tools/call` with arguments.
  - The client query string is still forwarded when the upstream URL has none. The Tradernet MCP does not document query-string credentials, but an operator can close the channel by putting any query on the upstream `url`, because then the configured query wins.
  - N-10 above (fixed in #38).
